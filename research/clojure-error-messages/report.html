Clojure's error messages

Why they read like Java stack traces, what has been tried, and how far an opt-in library can get before it needs the language's help.

The same mistake, four languages

A list of prices with one string in it. Every environment below sees the same bug; what differs is how much of what it knows reaches the person reading.

Not designedQuestion 1 · why
Six of fifteen runtime messages in the test corpus are authored by HotSpot or the JDK, in Java vocabulary. The JVM class file has nowhere to store a column, so a runtime error can never point at a sub-expression. Both are consequences of the hosting strategy, not choices about wording.
Tried twice, seriouslyQuestion 2 · attempts
Core did one redesign, in Clojure 1.10 (2018): error phases, ex-triage, and a REPL that prints two lines instead of a trace. The community has independently rebuilt message-rewriting tables at least four times and stack-frame filters at least six times. None of them share code.
Governance, not apathyQuestion 3 · barriers
The core team's position is on the record and consistent since 2011: improve messages, expose data, leave trace presentation and beginner rewrites to tools. A one-line message fix with a community patch took four years to ship.
Copy Ruby, not ElmQuestion 4 · other languages
Elm and Rust spend their whole budget at compile time and have almost no runtime error to design. Clojure's problem is a runtime problem. Ruby solved the same problem with third-party gems that were later bundled, then given a real hook.
Most of it, todayQuestion 5 · as a library
A 390-line library with no dependencies gets source excerpts, hidden frames, plain-language headlines, hints and "did you mean". It cannot get true columns, cannot hook clj -M script.clj at all, and cannot make the four REPL clients agree.
Question 1

Why are the messages like this?

Follow one piece of information — where in the source the error is — from the file to the printed message. It is destroyed twice and rewritten once by a party that has never heard of Clojure.

Five mechanisms, all visible in the source

Only lists have a position

The reader attaches :line/:column in exactly two places: ListReader and MetaReader when the target is a seq. Vectors, maps and sets get nothing; symbols are interned bare; keywords, numbers and strings cannot carry metadata at all. Syntax-quote deletes positions from everything a macro builds.

The class file has no column slot

The compiler carries the column all the way to code generation, then calls visitLineNumber(line, label). ASM's API has no column parameter and the class-file attribute has no field for one. Every runtime location in Clojure is capped at file:line, forever.

Core codes the happy path

clojure.core/+ inlines to Numbers.add, which does (Number)x with no type check first. The cast is a JVM checkcast, so the "cannot be cast to class java.lang.Number" text is HotSpot's. Same for the helpful NullPointerExceptions, which name Java parameters like "x".

Laziness moves the blame

(map f coll) runs f inside LazySeq.force, wherever the sequence is first walked. Bug 5 in the corpus builds a sequence on line 4 and fails on line 8 inside reduce. At the REPL, if the consumer is the printer, the message becomes "Error printing return value".

Macros inherit the call site

macroexpand1 copies no metadata onto the expansion, and syntax-quote stripped what there was, so every form a macro generates reports the line of the macro call. Clojure's own test suite notes it: :line meta on &form does not survive successive expansions.

Names are munged, calls are doubled

- becomes _, ? becomes _QMARK_, anonymous functions get a counter id that changes every run, and direct-linked functions emit both invokeStatic and invoke — so one call is two adjacent frames. Hence bugs.deep$parse_row$fn__147.invoke.

How much of a stack trace is yours

Fifteen realistic bugs, each run as a script so Clojure writes its full error report. Every frame in those reports classified by the class that owns it.

And a stance, not an oversight

The mechanics explain the shape. The reason the shape has not changed much is a position the core team has held and restated for fifteen years.

The core team is very interested in improving error messages, and relatively less interested in more code to manipulate stack traces… any old library code can reduce a stacktrace. Stuart Halloway, Clojure mailing list, 2011, in a thread titled "better error messages > smaller stack traces"
Does Clojure need to incorporate a bunch of changes in its 1.9 release cycle in order to provide a better experience for beginners? No. Who can make a better experience for beginners? Anybody! Stuart Halloway, "REPL-Driven Development", 2017
I do really want to see the actual stack trace so I don't think that should go away… a lot of people have poured time into this and the results are not (imo) better than the original. I say that not to throw water on it, but just to note that it seems easy but the details are complicated. Alex Miller, ask.clojure.org, 2021

Read together, these are a division of labour: core improves message text where Clojure authors it and exposes data for tools; presentation and beginner-friendly rewriting are the tools' job. That is exactly the space an opt-in library occupies — and it is an invitation, if you take it at face value.

Question 2

What has already been tried?

One serious redesign inside the language, and about a dozen attempts outside it, most of which rebuild the same two things from scratch.

Pattern 1 · rebuilt 4×

Message rewriting as a regex table. Babel's dictionary, Maria's template trie, rephrase's config, the 2016 catalog. Each maintained by one person or one classroom. rephrase reusing Babel's mappings in 2026 is the first time one table ever fed another.

Pattern 2 · rebuilt 6×

Stack-frame filters. pretty's rules, orchard's tooling regex, kaocha's filter list, Reveal's, pyro's, Babashka's. There is no shared definition of "a frame the user does not care about", in core or out of it.

Pattern 3 · the tell

Adoption follows bundling, not quality. expound has 20M downloads because figwheel and guardrails pull it in. Babel, the one project with actual classroom research behind it, has 309.

Question 3

What stands in the way?

Seven technical walls, four social ones. Two of the technical walls were discovered by trying, not by reading.

No columntechnical · unfixable in a library
The JVM's line-number table has no column field. A library can only guess; the prototype guesses from the innermost clojure.core frame's function name and labels the guess as one. Only the compiler could emit a side table.
The text isn't Clojure'stechnical · maintenance burden
Six of fifteen messages come from HotSpot or the JDK, and their wording changes between JDK versions — Babel's dictionary already carries three phrasings of the same ClassCastException. Any rewrite table inherits that churn.
Direct linking closes the doortechnical · discovered by experiment
clojure.main/main calls report-error with invokestatic — confirmed with javap on the shipped jar — so no library can change what clj -M script.clj prints. And the REPL captures its :caught default when it starts, while -e runs inside it, so clj -e "(install!)" -r silently does nothing. A user.clj on the classpath works; -e does not. Both pretty and this report's prototype are affected.
"User frame" is a hard-coded listtechnical · fixable upstream
ex-triage blames the first frame outside clojure.lang. and a fixed set of namespaces. JDK classes are not on it, so two of the fifteen bugs are reported at Integer.java:624 — a location the user cannot visit. Any library whose namespace is not on the list gets blamed for its callers' errors.
One printer per clienttechnical · coordination problem
clj, nREPL/CIDER, Calva, Cursive, Babashka, kaocha and clojure.test each render errors independently. Python hit the same wall with "Did you mean", which lives in PyErr_Display() and so does not appear in IPython.
Governancesocial · the long pole
Rich Hickey is BDFL; a signed contributor agreement is required; issues start on ask.clojure.org and reach JIRA only when the core team files them; patches are reviewed mainly in late alpha. A one-message fix with a patch attached took from May 2018 to March 2022. LLM-generated code is explicitly not acceptable under the agreement.
Nobody agrees what "better" issocial · substantive
Alex Miller thinks prettified traces "are not (imo) better than the original". Marceau, Fisler and Krishnamurthi found novices misread source highlighting as "edit here" and argue error messages should not propose solutions. Rust bans "did you mean" phrasing on principle. Python, Ruby, Elixir and Gleam shipped it anyway.
Question 4

How do the languages that do this well do it?

The two everyone names, Elm and Rust, are the two whose approach transfers least. Both spend their entire budget at compile time. Clojure's problem is a runtime problem.

Elm

A report is a four-field record — title, region, suggestions, message — rendered against the source text the compiler kept. Every principle people quote comes from two 2015 posts: show the code exactly as written, general context above the excerpt and specific hints below, a JSON form from day one, and "compilers should be assistants, not adversaries".

Why it doesn't transfer: "One big goal of Elm is to have no runtime errors. In practice, this is pretty much already how it goes." There is no runtime error subsystem to copy.

Rust

A diagnostic is data first: level, code, spans with labels, notes, help, and suggestions carrying an applicability confidence so rustfix can apply them mechanically. RFC 1644's stated goal was "draw inspiration from Elm". The style guide is worth stealing: only the help sub-diagnostic may propose a fix, and suggestions must not be phrased as questions.

The other half: a runtime panic is three lines and the backtrace is off unless you set an environment variable. Rich diagnostics at compile time, deliberate terseness at run time.

The two that actually apply

Python and Ruby are dynamic, host-constrained languages that fixed runtime errors in the last five years. Both did it the same way: add position information the VM was throwing away, then use it.

Python 3.11 · PEP 657

Added "a mapping from each bytecode instruction to the start and end column offsets" so a traceback can underline the failing sub-expression. The cost was measured and published — standard-library .pyc files grew 22% — and an opt-out shipped with it (-X no_debug_ranges). This is precisely the change Clojure would need, and precisely how to justify it.

Ruby 2.3 → 3.1 → 3.2

did_you_mean was a third-party gem in February 2014 and a default gem by Ruby 2.3 in December 2015. error_highlight, which puts a caret under the failing call by mapping a backtrace location back to its AST node, followed the same path into Ruby 3.1. Both worked by monkey-patching Exception#to_s, which broke tests and double-appended on re-raise — so Ruby 3.2 added Exception#detailed_message, a real hook, and the gems moved onto it.

The transferable precedent

Gem → bundled default → core hook. Each step justified by the previous step's adoption, and the hook added only once monkey-patching caused demonstrable breakage. That is the sequence the Clojure question is really asking about, and it is available without asking anyone's permission to start.

And one that shares Clojure's exact constraint

JRuby runs on the JVM and faces the same frame noise. It rebuilds Ruby-level backtraces from JVM frames plus its own interpreter frames, turning a ~60-line JVM trace into a 7-line Ruby one — and keeps the raw version one flag away. Groovy ships a sanitize call driven by a package-prefix list and logs the unfiltered trace so nothing is lost. Both chose filter by default, raw on request. Clojure's pst filters exactly two frame types.

Question 5

What can be done as an opt-in library?

Most of it. A 390-line library with no dependencies, written against hooks that already exist, closes most of the gap with Python and Ruby — and hits three walls that only core can move.

How to build it so it can win

Every previous attempt was one author, one regex table, one client. The thing worth building is the piece everyone keeps rewriting, packaged so the tools people already use can adopt the data without adopting a user interface.

  1. Analysis as data, rendering separate. One function returns a map, mirroring Elm's report record and Rust's diagnostic. Three renderers consume it: terminal, nREPL middleware, JSON. Reveal and orchard already consume ex-triage output and could consume a superset.
  2. Make the catalog the product. An EDN file of match-to-headline-and-hint rules, each pinned by a test to a captured exception — the way Elm's error-message-catalog is a collection of programs that trigger messages. Babel's dictionary, rephrase's config and the 2016 catalog are three seeds. Target Clojure-authored messages first: those strings are stable.
  3. Publish one definition of a "tooling frame" and let pretty, orchard, kaocha and Reveal depend on it instead of each carrying their own.
  4. Ship the JSON renderer early. Editors and CI are where buy-in is actually decided; Elm and Rust both shipped a machine format before anything adopted them.
  5. Then take three small asks upstream, with adoption numbers and the Ruby precedent attached.

The three asks only core can grant

Each is additive, each is motivated by a gap measured in this report, and each fits the constraint that a proposal should state a problem rather than arrive as a patch.

  • A dynamic error-printer var, read at each error, honoured by both the REPL and the script path. This removes the -e and invokestatic walls at once. It is the Exception#detailed_message moment: one var, no behaviour change unless bound.
  • Treat java.*, jdk.* and sun.* frames as non-user in ex-triage, and make the namespace list extensible. This alone fixes the Integer.java:624 locations for every client, with no new wording for anyone's tests to depend on.
  • Longer term, a column side table. The compiler already has the column at every visitLineNumber call. A custom class-file attribute mapping bytecode offsets to columns is the JVM analogue of PEP 657 — and like PEP 657 it should be prototyped in a fork with its size and time cost measured before anyone proposes it.
The risk worth naming

Marceau's finding is that a wrong hint is worse than no hint, because novices treat the tool as an oracle. Every catalog rule needs a captured exception it is tested against, hints should state facts about the failure rather than guess at the fix, and a guessed column must always say it is guessing. A tool that is confidently wrong once teaches people to stop reading it.
